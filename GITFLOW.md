# CLI AI Agent Git Flow & Push Policy

This document defines the automated Git workflow required for CLI-based AI agents (e.g., Aider, Claude Code, Cursor CLI, custom LLM CLI loops). It outlines mandatory commit cadence, branch hygiene, commit message standards, and remote synchronization.

---

## 1. Core Principles

1. **Short-Interval Synchronization**: AI agents must never accumulate large batches of uncommitted or unpushed work. Changes must be committed and pushed frequently at logical checkpoints.
2. **Atomic Commits**: Each commit must encapsulate a single, coherent change (e.g., one bug fix, one unit test, one refactored function).
3. **Traceability & Attribution**: Every commit message and pull request must explicitly state that it was generated by an AI assistant, detailing the intent, context, and verification steps.
4. **Non-Destructive Operations**: Automated agents are strictly forbidden from executing destructive Git operations (e.g., `git push --force`, `git reset --hard`) on protected branches (`main`, `master`, `develop`, `staging`).

---

## 2. Commit Cadence & Push Frequency

AI agents must trigger a commit and push cycle based on the following thresholds:

### When to Commit and Push
- **Every Completed Task / Subtask**: Commit and push immediately after finishing a self-contained unit of work (e.g., creating a module, writing a test suite, fixing a lint error).
- **Time/Turn-Based Interval**: If a task spans multiple back-and-forth prompt cycles, commit and push at least once every **10–15 minutes** or after every **2–3 agent execution iterations**, provided the working directory passes basic syntax checks.
- **Before Tool Switching or Large File Generation**: Save and push working state before attempting risky, expansive refactors or complex migrations.
- **Milestone Completion**: Push immediately when tests pass and feature objectives are achieved.

### Pre-Commit Checklist for AI
Before committing, the agent must ensure:
- [ ] Code compiles or passes basic static analysis/linting.
- [ ] No temporary debug artifacts, API keys, or `.env` files are staged.
- [ ] No unstaged conflicting edits remain in the working tree.

## 3. Branching Strategy

| Branch Pattern | Purpose | Automated Push Rules |
| :--- | :--- | :--- |
| `main` / `master` | Production-ready code. | **Direct pushes prohibited.** AI must work on feature/task branches. |
| `feature/ai-<task-name>` | New capabilities or enhancements. | AI must push after every logical milestone. |
| `fix/ai-<bug-description>` | Targeted bug fixes or patches. | AI must push as soon as the test passes. |
| `refactor/ai-<component>` | Structural and performance refactors. | Frequent pushes with incremental validation. |
| `chore/ai-<maintenance>` | Dependency updates, documentation, linting. | Single atomic commit and push. |

### Branch Naming Convention
```bash
<type>/ai-<short-description>-<issue-or-task-id>
```
*Example:* `feature/ai-user-auth-endpoints-issue-42`

## 4. Commit Naming & Message Structure

All commits generated by the CLI AI must adhere to the **Conventional Commits** specification, extended with descriptive AI metadata.

### Commit Format

```text
<type>(<scope>): <concise imperative summary (max 50 chars)>

[Optional body: detailed explanation of changes, rationale, and impact]

- Key change 1
- Key change 2

[Optional footer(s)]
Co-authored-by: AI Assistant <cli-agent@local>
Refs: #<issue-number>
```

### Commit Types
- `feat`: A new feature or capability.
- `fix`: A bug fix.
- `refactor`: Code change that neither fixes a bug nor adds a feature.
- `test`: Adding missing tests or correcting existing tests.
- `docs`: Documentation only changes.
- `style`: Formatting, missing semicolons, whitespace (no functional change).
- `chore`: Maintenance, build tasks, package updates.

### Good Commit Message Examples

#### Example 1: Feature Milestone
```text
feat(auth): implement JWT token verification middleware

- Add verifyToken utility using jose library
- Wire middleware into protected API router
- Add unit tests covering expired and malformed tokens

Co-authored-by: AI Assistant <cli-agent@local>
```

#### Example 2: Incremental Push during long task
```text
refactor(database): extract query builder logic into separate service

- Split monolithic user repository into query builder and executor
- Update repository interface definitions
- Note: Integration tests pending in subsequent commit

Co-authored-by: AI Assistant <cli-agent@local>
```

## 5. Automated CLI Commands Reference

When operating autonomously or semi-autonomously, the AI CLI agent must follow this exact shell sequence:

```bash
# 1. Verify branch and status
git status --porcelain

# 2. Add modified files deliberately (avoid blanket `git add .` if untracked junk exists)
git add <path/to/modified/files>

# 3. Commit with structured title and body
git commit -m "feat(ui): add responsive navigation drawer" \
           -m "- Implement sliding animation with Tailwind transitions" \
           -m "- Add mobile breakpoint hook and toggle state" \
           -m "Co-authored-by: AI Assistant <cli-agent@local>"

# 4. Push immediately to remote branch with upstream tracking
git push -u origin HEAD
```

---

## 6. Safety & Conflict Handling

1. **Remote Ahead of Local**: If the remote has changes, run `git pull --rebase origin <branch>` before attempting the next push. Do not force push.
2. **Merge Conflicts**: If a rebase or merge produces conflicts, the AI agent must stop, report the conflicting files and line numbers clearly to the human operator, and await guidance or systematically resolve only its own staged diffs.
3. **Secrets Detection**: Never commit `.env*`, `*.pem`, `*.key`, `id_rsa`, or strings matching credential patterns.
